# Bringing Android runtime checkpoints to a new game

[简体中文](CHECKPOINT_ONBOARDING.md)

Start with one manual capture followed by a restore in a fresh process. Find the first operation that returned an error. Use that evidence to decide whether the port needs **version-specific data**, **an engine-specific operation**, or **support for a resource in the shared backend**. If the logs identify only a stage, record the stage and the observation that would narrow it down. This guide covers the runtime snapshot backend selected by `porter port --field-checkpoint`. [Build instructions](DEVELOPMENT_GUIDE.md#runtime-checkpoints)

## Collect both logs from the same attempt

1. Confirm that the game reaches a playable scene. Record the Title ID, package name, host build, data pack version, device, and Vulkan driver. Read `# BUILD_ID` from the installed pack's `mods/main.fixups.tsv` and, when present, `mods/sdk.fixups.tsv`. Track regional releases, game updates, and SDK builds separately. Single-screen NVN/Vulkan ports using the default native-keyboard GameActivity enable checkpoints automatically for entries in the [checkpoint build list](../nxnative/dm/games/checkpoint_builds.tsv). To bring up a title, add its Title ID and main Build ID locally and rebuild. Publish the entry after the acceptance checks below pass. If the save action is missing, check the build match, options, Activity, and installed host before investigating capture. [Module identity](../nxnative/dm/host/loader.c) · [Installed APK capability checks](../porter/host.py)
2. Select **Save checkpoint** in a recognizable scene. Record the player's position or menu state, and the result shown in the UI. Copy the capture process's `log.txt` before the next launch. If capture fails, record that outcome. A restore offered on the next launch may refer to an older snapshot.
3. After a successful capture, end the game process. Relaunch, select restore, and copy the new process's `log.txt`. The host writes stderr to the app's files directory and rotates the previous log to `log.prev.txt` on each cold launch. If exactly one launch has occurred, both logs are still available. For an Android crash, also collect logcat for the matching time window. Keep the full logs. Several restore errors containing `refused` go directly to stderr without a `[snapshot]` prefix. [Log setup and rotation](../nxnative/dm/android/front_android.c)

Run the following commands from a local directory dedicated to this attempt. Substitute the device serial and package name. The example assumes adb can read the external app files directory. If the host falls back to internal storage, a debuggable package can expose the current log through `adb -s "$serial" exec-out run-as "$pkg" cat files/log.txt`.

```sh
serial='your-device-serial'
pkg='your.package.name'
files="/sdcard/Android/data/$pkg/files"
# After capture completes, before relaunching
adb -s "$serial" pull "$files/log.txt" capture.log
# After selecting restore in the new process
adb -s "$serial" pull "$files/log.txt" restore.log
# Recover a missed capture log if there has been exactly one cold launch
adb -s "$serial" pull "$files/log.prev.txt" previous.log
rg -an -C 3 '\[snapshot\]|refused|FATAL|failed|\[RED\]' capture.log restore.log
```

## Trace the first failure to a call

| Stage and searchable log text | What the log establishes | Next check |
| --- | --- | --- |
| Startup reports `snapshot layout setup failed`, `snapshot module baseline failed`, or `unexpected checkpoint heap constructor site` | The first message covers module and memory layout initialization. The second identifies module baseline creation. The third means a heap rule matched, but the instruction-site check failed. | For a layout failure, inspect the actual module list, the presence of `nro.tsv`, and the address reservation result. For a constructor failure, verify the main Build ID, rewritten image, and heap rule for that build. Check whether the pack contains artifacts from different builds. [Layout checks](../nxnative/dm/android/checkpoint_modules.inc) · [Loader](../nxnative/dm/host/loader.c) |
| Capture reports `pending thread=`, `no SVC gate frame`, `frame outside checkpoint memory`, or a nonzero `thread sample:` result | The summary can carry an earlier failure from pausing threads, capturing a wait, or synchronizing audio or graphics. | Find the first specific thread handle, wait/SVC, PC or stack, or thread that failed to pause. If it happens during a scene transition, compare with a stable scene on the same build. A confirmed unsupported wait type needs capture and restore support in the thread module. [Capture order](../nxnative/dm/android/checkpoint/runtime.c) · [Wait-context checks](../nxnative/dm/android/checkpoint_wait.inc) |
| Several of `scene events result=`, `scene through bindings result=`, `scene through modules result=`, and `scene core result=` report the same error | In `survey_core()`, each step runs only while `rc == 0`. Later lines can repeat the first error. The events summary also covers earlier file, mount, audio, and graphics operations. | Inspect calls between the last success and the first failure. If events succeeded and bindings first reported an error, inspect the binding records. For `unsupported pool` or `cannot capture image`, keep the pool flags or the image format, sample count, and return code. If only summaries are available, log the operation and return code within that interval. [Section write order](../nxnative/dm/android/checkpoint/runtime.c) · [GPU pools](../nxnative/dm/android/checkpoint_pools.inc) |
| The next launch offers no restore, or reports `current checkpoint could not be verified` | Startup checks the current-slot marker, the directory name, and whether every required section is a nonempty regular file. | Check the previous capture's `scene core result`, the package name, and whether the slot was published. Resolve reported storage exhaustion or file I/O errors first. Preserve the files so you can distinguish a publication failure from a read failure. [Slot publication and validation](../nxnative/dm/android/checkpoint/slot.c) |
| Restore reports `scene guest address space refused`, `scene module data refused`, `scene GPU pools refused`, or `scene image storage refused` | Each message identifies a subsystem or group of calls. The final `restored session ended, result=1` has lost the underlying error code. | Read the earlier code, establish which build created the snapshot, and retest with a fresh capture on the same host and pack. The address-space stage covers module reservation, baseline creation, and memory restore. Module data also covers SDK clock rebinding. Identify the failing check before assigning a fix. [Restore order and error conversion](../nxnative/dm/android/checkpoint/restore.c) |
| After `resumed playable field session`, the game crashes, displays a black screen, or fails to save in-game | The host reached thread release. Thread continuation, rendering, audio, and in-game saves can still fail independently. | Inspect subsequent `field continuation` messages, crash stacks, presented frames, and response to input. `game save commit refused` comes from the in-game save transaction. A conflict reported as `-ESTALE` can occur when the same file changed after capture. Record the order of the two writes and the affected files to distinguish a conflict from a write failure. [Thread release](../nxnative/dm/android/checkpoint/restore.c) · [In-game commit](../nxnative/dm/host/hle_fs.c) · [Merge and backup](../nxnative/dm/android/checkpoint/save_commit.c) |

## Choose where to make the change

| Decision | Evidence that supports it | Smallest change and how to verify it |
| --- | --- | --- |
| **Add version-specific configuration** | The target build uses a known mechanism and the existing table can describe the entire difference. Examples include a UE heap constructor at a new call site or the same SDK clock binding at a new slot. A missing row alone leaves the cause open. | Check the game's `checkpoint_heap.tsv` or the shared `checkpoint_sdk_clock.tsv`, as applicable. Verify which table was compiled and which module Build ID matched at runtime. Confirm the expected branch ran, then cold-restore the game. SDK clock rows are reusable across titles with the same SDK Build ID. [Build-time table selection](../nxnative/dm/android/build.py) · [SDK clock rules](../nxnative/dm/games/checkpoint_sdk_clock.tsv) |
| **Reuse or add a narrow interface** | Capture happens at the same stage and has the same success condition, but the engine needs a different operation. Confirm the difference with a controlled comparison and the failing call’s return value. | Implement the operation in the module that owns the state. Reuse an existing interface when it fits. Document when the call runs and what it returns. Test the affected path, an unaffected path, and pause cleanup on failure. [Capture and cleanup](../nxnative/dm/android/checkpoint/runtime.c) |
| **Extend the shared backend** | The failure identifies a missing resource representation, serialization step, reconstruction step, or reference check. Examples include confirming that `nro.tsv` triggers the dynamic-module rejection or that a valid GPU pool type cannot survive capture and cold restore. A single title can expose a shared subsystem gap. | Implement both halves in the owning module, such as the loader, threads, GPU, audio, or filesystem. Preserve version and integrity checks, slot publication order, and the conditions for releasing threads. Verify a round trip for the new resource, rejection of damaged or mismatched inputs, and continued support for existing samples. [Module support checks](../nxnative/dm/android/checkpoint_modules.inc) · [Section restore](../nxnative/dm/android/checkpoint/restore.c) |

**Sometimes the evidence warrants no code change yet.** An older Octopath Traveler II prototype snapshot returned `-EINVAL` during GPU pool restore. A fresh snapshot from the tested build restored on the same phone. The record does not identify which pool check rejected the older sample. Preserve the old sample and report the compatibility range you observed. If reading older snapshots is part of the task, trace the corresponding format or validation branch. [Device verification record](ARCHITECTURE.md#lossless-dll-import-and-frame-generation-timing)

## Verify the port

- **Target scene.** Save on the target build, restore in a fresh process, and confirm the recorded position or menu state. Check sustained frame presentation, input, and audio when the scene has sound. Write an in-game save to a test slot, cold-start normally, and load that slot. Keep both logs and record the device, build, scene, and observed results. Mark only the combinations exercised as passing.
- **Change-specific checks.** For a table change, exercise matching and nonmatching builds. For a narrow interface, exercise scenes that trigger and bypass it. For shared-backend work, cover resource round trips and rejection cases. When save merging changes, use test saves to verify that independent slots survive, divergent edits to the same file trigger a conflict, and the backup is made before overwrite. [Save verification examples](ARCHITECTURE.md#lossless-dll-import-and-frame-generation-timing)
- **Existing tools.** Run `python3 devtools/runtime_checkpoint/verify_runtime.py --help` for the device probe's host build, module, and driver arguments. The probe exercises reconstruction of specific resources in a fresh process. Check gameplay, presentation, and in-game save loading in the target game. [Device probe](../devtools/runtime_checkpoint/verify_runtime.py) · [Slot tests](../tests/test_checkpoint_android.py)
